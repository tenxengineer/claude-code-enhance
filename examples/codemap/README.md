# Project Codemap — Format and Conventions

The codemap is a small set of files at `<project-root>/.codemap/` that
captures architectural narrative, change-frequency heat map, and recent
activity. Loaded by the `inject-project-codemap.sh` SessionStart hook
when Claude Code starts in any directory whose ancestor contains
`.codemap/`.

## Why this exists

Pure semantic tools (LSPs, vector DBs, grep) answer **structural**
questions: "where is X defined?", "what calls Y?". They don't answer
**narrative** questions: "what's the architecture?", "what's hot?",
"what's in flight?".

A senior engineer who's been on the codebase for 18 months has those
narrative answers in their head. The codemap captures them in files so
your AI agent has them too.

## Files

### `overview.md` — hand-written, rarely changes

Architectural narrative — the document you'd give a new hire. Covers:

- What the product is (1 paragraph)
- Top-level layout (directories, what lives where)
- Layer boundaries (what talks to what; what's sacred)
- Cross-cutting concerns (auth, logging, telemetry, error handling)
- Hot subsystems (the most complex/risky/high-traffic parts, with cross-references to lessons)
- Tech stack defaults
- Boundaries to know about (anti-patterns specific to THIS codebase)

Update only when architecture genuinely changes. Auto-generated
architecture summaries are usually generic and miss load-bearing
decisions — write this by hand.

### `hotfiles.md` — auto-generated, refresh weekly

Top files by 90-day change frequency, with one-line annotations and a
"patterns to notice" paragraph. Generated by:

```bash
git log --since="90 days ago" --name-only --pretty=format: \
  | grep -v '^$' | sort | uniq -c | sort -rn | head -20
```

The `/refresh-codemap` skill regenerates this and prompts you to
annotate. Why the human annotation? File names alone don't tell you
why a file is hot — is it a stable abstraction with frequent feature
additions, or a brittle module that keeps breaking? The annotation
captures that.

### `recent.md` — auto-generated, refresh weekly

Last 30 days of work summarized by theme. Generated by:

```bash
git log --since="30 days ago" --pretty="format:%ad|%s" --date=short
```

Then summarized into "dominant theme" + "milestones completed" +
"what this implies for any work I do" sections. Not a commit log
replay — judgment-laden, action-oriented.

The `/refresh-codemap` skill also regenerates this.

## Bootstrapping a new project's codemap

```bash
cd <project>
mkdir .codemap
# Copy templates and edit:
cp <plugin-repo>/examples/codemap/overview.md   .codemap/overview.md
# Edit overview.md — replace placeholders with your project's specifics

# Auto-generate the rest:
/refresh-codemap
# (the skill reads git history and writes hotfiles.md + recent.md)
```

After this:

- The `inject-project-codemap.sh` SessionStart hook (if you've wired it)
  will inject the codemap on every session in that project's directory.
- The `/enhance` skill will load the codemap when producing enhanced
  prompts, giving real file references and current sprint context.

## What NOT to put in the codemap

- Code structure that LSPs can answer (find_symbol, find_references) →
  use Serena MCP for those queries on demand
- Git blame ownership at file granularity (large repos make this
  unmaintainable) → use git directly when needed
- Dependency graph (large, churns frequently) → let LSPs answer this
- Per-function documentation (belongs in code comments or docs/)
- Sensitive secrets, credentials, internal-only architecture details
  if you plan to commit `.codemap/` to a public repo

## Whether to commit `.codemap/`

**Pros of committing:** team shares the same codemap, history shows how
architecture evolved, contributors see structure quickly.

**Pros of gitignoring:** stays personal, generated artifacts (hotfiles,
recent) don't pollute PR diffs, you can iterate freely.

**Suggested:** commit `overview.md` (hand-written, evolves slowly), but
add `hotfiles.md`, `recent.md` to `.gitignore` (auto-generated, churns
weekly). This way the team shares architecture but each contributor
has fresh activity data when they session-start.
